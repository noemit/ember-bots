# Desktop updates and release gates

**Release control:** updater configuration is not publication authorization. Each release requires
explicit owner approval and the gates below for every platform it offers. The next-contract Latest release requires all advertised downloads; missing platforms block
promotion. See the canonical [release contract](../RELEASES.md) for names and manual Windows policy.
See [Versioning](../VERSIONING.md) for the separate release authorization and version rules.

## Daily checks

Supported stable desktop installations check GitHub roughly once a day while Ember is open:
24 hours plus a persisted random delay of up to 15 minutes. Settings → General → **Check for Ember
updates daily and notify me** is on by default. Switching it off leaves **Check now** available in
that same Settings section, alongside the installed version, last result and check time.

Attempt time and the next check deadline are persisted, so restarting or waking Ember catches up
only when overdue; missed days are never replayed. One desktop-owned scheduler prevents overlapping
checks. Background failures stay quiet in Settings until the next daily attempt; manual checking
remains available. The top bar shows available updates, requested downloads and installer problems,
not idle/checking status or background check failures. Ember never downloads, installs or restarts
automatically. There is no closed-app background service. Development, Canary and unsupported
packages retain the eligibility rules below.

## Supported packages

Updates use `electron-updater` and the public GitHub **stable** releases of
[`noemit/ember-bots`](https://github.com/noemit/ember-bots/releases). The packaged
`resources/app-update.yml` is generated by electron-builder; do not replace it with a runtime feed
URL or embed a GitHub token. Drafts and prereleases are not the stable distribution channel.
Packaging scripts explicitly use `--publish never`; publication remains a separate reviewed action.
Only the release scripts `dist:mac`, `dist:win` and `dist:linux` inject the mandatory packaged
`emberUpdateChannel: "stable"` marker through builder `extraMetadata`. Main reads that marker from
`app.getAppPath()/package.json`; without it, updates are disabled even for a packaged app with a
stable-looking version. Do not put the marker in the source package metadata or shared builder config.
Generic `dist`, `dist:mac:local` and the unchanged unsigned native CI packaging path leave it absent,
so development/test packages cannot discover or install production updates.

| Installed package | Update artifact | Channel metadata | Requirements |
| --- | --- | --- | --- |
| macOS app installed from DMG or ZIP | macOS ZIP (DMG remains the manual installer) | `latest-mac.yml` | Signed Developer ID app, hardened runtime, notarized and stapled; both DMG **and ZIP** must be built/uploaded |
| Windows NSIS install | Signed NSIS setup EXE | `latest.yml` | Authenticode signing and a nonempty, correct publisher allowlist in the installed `app-update.yml` |
| Linux AppImage | AppImage | `latest-linux.yml` | Run the actual AppImage from a writable location; retain its embedded block map |
| Linux tar.gz, Windows portable ZIP, source/dev runs, standalone Tinder/Kiln | None | None | Manual download/replacement; these are not supported automatic-update installs |

A current installation without updater code cannot discover its first updater-enabled build.
**Bootstrap manually**: download that build from the Releases page, quit Ember, replace/install it,
and reopen. Preserve the user's data directory. Do not promise an update notification in a build
without updater support.

Live signed macOS upgrade installation is a separate check from signing, notarization and fresh
startup. For 1.24.0 the owner explicitly approved publication with that live check deferred; it
remains unverified, not a known failure or a passed test. An updater-enabled older Mac installation
can exercise it against the public release now. A newer release needs its own test or explicit
deferral; it must not inherit a previous release's waiver. See the [release record](releases/1.24.0.md).

## Signing is mandatory for release

Use `bun run dist:mac` and `bun run dist:win` for release candidates. Both request
`forceCodeSigning=true`; missing signing credentials must fail the build. macOS also sets
`EMBER_RELEASE=1`, making the existing notarization hook reject missing notarization credentials.
All three release distribution scripts also inject `emberUpdateChannel=stable`; verify that marker
in the final packaged `package.json` before release. Signing alone does not enable the updater.
Do not remove these flags, disable signature checks, use ad-hoc signing, or advertise a local/CI
unsigned build as an automatic-update release. Owner-approved unsigned Windows manual distribution
is a separate path: disclose it, omit latest.yml and the stable updater marker, and keep signature
verification enabled. `dist`, `dist:mac:local` and direct builder invocations are development
paths, not release signing gates. The existing Windows native-test workflow is intentionally
unchanged: its unsigned test artifacts are not release-ready and its upload list is not the updater
publication checklist.

### macOS prerequisites and verification

Build on macOS with the owner's real **Developer ID Application** certificate and private key
available to electron-builder (keychain or its supported private credential mechanism). The existing
notarization hook requires `APPLE_ID`, `APPLE_PASSWORD` (app-specific password), and `APPLE_TEAM_ID`
in the release shell. Credentials and identity values belong in private configuration, never here.
Keep the existing entitlements, hardened runtime, signing, notarization and stapling flow.

After packaging, mount the DMG and verify the **app inside it**, not the unsigned DMG container:
`codesign --verify --deep --strict <mounted-app>`, `spctl -a -vvv -t exec <mounted-app>`, and
`xcrun stapler validate <mounted-app>`. Also unpack the ZIP and run those checks on its app.
Confirm the bundled `Contents/Resources/kiln` has the correct Mach-O architecture. A package that
passes checks on the build machine alone is not evidence of A→B installation on another Mac.

### Windows prerequisites and publisher rules

Build on Windows with a valid, trusted code-signing certificate **and access to its private key**,
Windows signing tools, and working timestamp service/network access. Supported private setup is
one of:

- PKCS#12 certificate via `WIN_CSC_LINK` (or builder's `CSC_LINK` fallback) and
  `WIN_CSC_KEY_PASSWORD` (or `CSC_KEY_PASSWORD` fallback).
- A certificate in the Windows certificate store, selected with a privately reviewed builder overlay
  using `win.signtoolOptions.certificateSha1` or `certificateSubjectName`. Prefer the actual
  thumbprint when selecting among similar certificates. Hardware-backed keys also need their
  vendor's signing provider available to the build user.

There is deliberately **no invented publisher or certificate subject** in `package.json`.
With the default SignTool path, electron-builder 26.18.0 extracts the real signing certificate's
common name and writes `publisherName` into the packaged `resources/app-update.yml`.
`win.verifyUpdateCodeSignature` remains explicitly `true`. Before approving the first release,
inspect that generated file: `publisherName` must be nonempty and match the actual trusted signing
identity. Missing/empty/null publisher configuration is a release blocker, not a workaround.

If using an explicit allowlist, set `win.signtoolOptions.publisherName` to the exact certificate
common name(s) verified from the signing certificate, never a product name guessed from this repo.
Never set it to `null` or disable `verifyUpdateCodeSignature`. Azure Trusted Signing is not configured
here; adopting it requires a reviewed `win.azureSignOptions` setup including its real publisher name
because builder cannot infer that allowlist from Azure. Do not silently switch signing providers.
Certificate renewal with the same publisher still needs testing; a changed publisher needs a planned
bridge release whose installed allowlist trusts the next certificate before it is used.

Verify the packaged `Ember.exe` and NSIS installer with `Get-AuthenticodeSignature` (Status `Valid`,
expected signer and timestamp) and `signtool verify /pa /all /v <file>`. Inspect the installed feed
configuration, then test signed A→B NSIS installation, relaunch/version, retained settings and bundled
Kiln lifecycle on Windows. Test rejection of an untrusted/mismatched publisher. No signing identity
has been supplied or validated by this configuration change; these are outstanding release gates.

## Artifact assembly (only after release authorization)

Build all platform candidates from the same reviewed version/commit in clean output directories.
Give the owner the macOS build instructions **before** starting Linux release packaging. Preserve
all native packaged OAuth, codemode self-test and lifecycle checks in
[development](development.md#packaging); updater work does not replace them.

Stage these files, keeping their generated filenames and bytes:

| Platform | Upload set |
| --- | --- |
| macOS | Contract DMG and ZIP, every generated `.blockmap`, `latest-mac.yml`, Tinder, `SHA256SUMS-macos.txt` |
| Windows | Contract setup EXE and portable ZIP, every generated `.blockmap`, Tinder, `SHA256SUMS-windows.txt`; `latest.yml` **only for signed updater releases** |
| Linux | Contract AppImage and tar.gz, `latest-linux.yml`, Tinder, `SHA256SUMS-linux.txt` |

Exact filenames and permanent URLs live in [RELEASES.md](../RELEASES.md).

Builder emits the final contract filenames; never rename them. Build ZIP and DMG together:
macOS metadata prefers ZIP for its legacy `path`/`sha512`, and its `files` list can also contain the
DMG. Mac ZIP and DMG and Windows NSIS produce external `.blockmap` files when enabled by the builder;
upload all emitted maps. Linux AppImage uses an **embedded** block map (`blockMapSize` in YAML), not
a required separate `.AppImage.blockmap`. Never strip, recompress, re-sign, notarize or otherwise
modify artifacts after metadata/checksums are calculated. Rebuild metadata/checksums if bytes change.

Metadata contains base64 **SHA-512**, sizes and artifact URLs; `SHA256SUMS-*.txt` is a separate human
verification convenience, not a replacement. Generate each platform checksum manifest over its final
installer/archive/binary files, emitted blockmaps **and channel YAML** (do not hash the manifest into
itself). Preserve the existing release asset index/list, platform checksums, manual archives and CLI
assets; add metadata/maps rather than replacing that distribution surface. Do not upload unpacked
apps, builder debug/effective config files or private signing inputs.

For multiple architectures, macOS and Windows share their platform channel YAML: gather all artifacts
first and verify that its `files` list covers every supported architecture. Separate builds can
overwrite that YAML; never upload the last architecture's file over another without a reviewed merged
index. Use a single multi-architecture builder invocation where supported. Linux x64 uses
`latest-linux.yml`; other Linux architectures have separate generated files (for example,
`latest-linux-arm64.yml`), which must also be uploaded unchanged. Inspect every referenced URL and
verify its SHA-512/size against the staged bytes. Missing referenced assets or filename collisions
block release. Do not hand-edit hashes to fit a renamed or modified artifact.

Upload and audit the full set on an authorized **draft** release first; do not expose a public stable
release with partial metadata. Check its tag equals the packaged version, the GitHub release is neither
prerelease nor missing assets, and the final asset index/checksum manifests remain intact before
publishing. Never replace bytes on an already published version; correct a release with a new patch.
Use the audited promotion command in [RELEASES.md](../RELEASES.md), not an unaudited Latest toggle.
This document does not authorize any of those publication steps.

## Evidence and outstanding gates

Local Linux-only probe of electron-builder 26.18.0 (Electron 42.10.1): an isolated minimal fixture,
using this GitHub publish config, built an unsigned **private, non-distributable** x64 AppImage with
`--publish never`. It emitted `latest-linux.yml` with SHA-512, size and `blockMapSize`, and packaged
`app-update.yml` naming `noemit/ember-bots`, `latest`. No external AppImage blockmap was emitted.
The combined AppImage/tar probe exceeded the local time limit; AppImage-only completed. This is
metadata evidence, not a production Ember/native smoke test. Mac/Windows output behavior above is
also checked against the pinned builder source; native signed packages were not produced here.

The fixed-filename contract was additionally checked with a real private Linux x64 Ember build
at the unchanged development version 1.23.0, **without** the stable updater marker or publication.
Normal packaging emitted `Ember-linux-x64.AppImage`; its generated YAML URL, SHA-512, byte size and
embedded map size passed the new validator. Builder normally expands AppImage’s architecture macro
to `x86_64`, so the pre-pack hook selects the final `x64` name before generation. An initial combined
AppImage/tar build timed out; a separate tar retry with `compression=store` completed as
`Ember-linux-x64.tar.gz` and passed `tar -tzf`. This confirms naming/archive integrity, not a native
GUI/update smoke test or production release. The original 1.23.0 assets remain untouched.

A second private Linux fixture passed installed AppImage **900.0.1→900.0.2** using the current compiled
`UpdateController`, the real electron-updater AppImage installer, a loopback-only generic HTTP feed,
a separate synthetic profile and a writable installed copy. Explicit check found B; explicit download
verified B without changing installed A; explicit restart replaced the installed file with B's exact
bytes, relaunched packaged B and retained a synthetic setting. `APPIMAGE_EXTRACT_AND_RUN=1` exercised
the no-FUSE path. The fixture server lacked multipart-range support, so differential download failed
and the verified **full-download fallback** succeeded. This does not establish differential success,
FUSE mounting, the full Ember GUI/bundled-Kiln shutdown path or a production GitHub A→B release.
No production feed override or public release was used.

Before publishing a release:

- Run `bun run check` and all relevant native/packaged regressions on their actual platforms.
- Verify final signed/notarized macOS DMG **and ZIP**, metadata, blockmaps, hashes and architecture.
  Keep the accepted deferred Mac A→B test recorded until the next update actually exercises it.
- If offering Windows automatic updates, establish the real Windows signing identity, verify embedded publisher
  allowlist and signatures, and pass signed NSIS A→B, relaunch and mismatched-publisher rejection checks.
- Exercise AppImage A→B from a writable location on Linux, and confirm tar installs stay manual.
- Audit the complete staged upload set/index and each YAML reference/hash, including all architectures.
- Obtain explicit owner approval for publication. No bump, tag, workflow edit or public upload
  is authorized merely by implementing this configuration.

## Next-contract macOS commands

After the owner authorizes and tags the next release (example `v1.24.0`), with the signing and
notarization prerequisites above already configured privately:

```sh
# From your existing repository; leave its branch and working files untouched.
git fetch origin tag v1.24.0
mkdir -p "$HOME/.ember-worktrees"
git worktree add --detach "$HOME/.ember-worktrees/ember-release-1.24.0" v1.24.0
cd "$HOME/.ember-worktrees/ember-release-1.24.0"
test "$(uname -m)" = arm64
bun install --frozen-lockfile
(cd packages/kiln && bun install --frozen-lockfile)
bun run dist:mac --arm64
bun run dist:cli
hdiutil attach release/Ember-macos-arm64.dmg -mountpoint /tmp/ember-release-mount
codesign --verify --deep --strict /tmp/ember-release-mount/Ember.app
spctl -a -vvv -t exec /tmp/ember-release-mount/Ember.app
xcrun stapler validate /tmp/ember-release-mount/Ember.app
file /tmp/ember-release-mount/Ember.app/Contents/Resources/kiln
hdiutil detach /tmp/ember-release-mount
ZIP_CHECK=$(mktemp -d)
ditto -x -k release/Ember-macos-arm64.zip "$ZIP_CHECK"
codesign --verify --deep --strict "$ZIP_CHECK/Ember.app"
spctl -a -vvv -t exec "$ZIP_CHECK/Ember.app"
xcrun stapler validate "$ZIP_CHECK/Ember.app"
file "$ZIP_CHECK/Ember.app/Contents/Resources/kiln"
EMBER_PACKAGED_EXECUTABLE="$ZIP_CHECK/Ember.app/Contents/MacOS/Ember" \
  bunx --no-install playwright test --config playwright.packaged.config.ts
node scripts/release-assets.mjs checksums release macos 1.24.0 manual
```

Confirm both `file` results are Mach-O arm64 and the packaged stable marker is present. Upload only
the contract files, generated maps, channel YAML and checksum manifest to the authorized draft.
Do not upload unpacked apps or the whole `release/` directory. Do not use these commands to rebuild
or alter the existing 1.23.0 release. Keep existing tag builds on their original scripts and names.
